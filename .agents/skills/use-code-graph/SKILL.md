# Навигация по коду через code-graph

MCP-сервер code-graph строит индекс проекта (AST-дампы классов, граф вызовов, обратный индекс вызовов, REST-эндпоинты) в `<project>/.code-graph/`. Чтение индексированных данных почти всегда дешевле grep-раундов: точечный запрос возвращает атрибуцию (класс, перегрузка, файл:строка) без чтения самих файлов.

## Порядок работы в новом чате

1. Если `.code-graph` отсутствует или устарел — вызвать `analyze_project` с путём к корню проекта. Это единственная дорогая операция, не повторяйте её в рамках одного чата без причины.
2. Проверка свежести: один раз прочитать `.code-graph/meta.json` (там хэш коммита) и сверить с `git rev-parse HEAD`. Устарел после pull/переключения ветки/правок кода → пересобрать `analyze_project`.
3. Дальше только точечные инструменты — никогда не читать `graph.tsv` / `called_by.tsv` / `classes/*.json` целиком через grep или Read без фильтра.

## Какой инструмент для какого вопроса

| Вопрос | Инструмент |
|---|---|
| Что за класс: поля, методы, аннотации | `get_class` (полный FQN) |
| Кто вызывает метод/класс | `get_called_by` с `target="ИмяКласса#метод"` — всегда передавайте `target`, без него вернётся весь called_by.tsv |
| Что вызывает метод / где autowire-связи | `get_graph` с `edge_type` и/или `contains` — полный граф без фильтра не читать |
| Какие REST-эндпоинты есть | `get_endpoints` — только если роутинг реально нужен: это сотни записей |
| Сводка проекта (сборка, Boot-версия, пакет) | `get_meta` — дёшево, можно первым вызовом |
| Все классы проекта | `list_classes` — только если нужен именно обзор |

Типы рёбер `get_graph`: `extends`, `implements`, `stereotype` (@Service/@Component/@RestController), `autowire_field`, `call`, `instantiate`, `has_transaction`, `listens_to_event`, `declares_bean`.

## Типовые сценарии

- «Где объявлен метод X» → `get_graph` c `contains="X"` или `get_class` по классу-владельцу.
- «Кто использует сервис Y» → `get_graph` с `edge_type="autowire_field", contains="Y"`; вызовы — `get_called_by` с `target="Y"`.
- «Что происходит при запросе /path» → `get_endpoints` (можно прочитать глазами и взять нужную строку, не отдавая весь список модели целиком — на практике фильтруйте вывод), затем `get_class` хендлера.
- Влияние изменения сигнатуры → `get_called_by` по методу + `get_graph` по классу.
- Spring-связка: транзакции → `edge_type="has_transaction"`; слушатели событий → `edge_type="listens_to_event"`; объявленные бины → `edge_type="declares_bean"`.

## Правила экономии

- Один точный запрос вместо серии grep: подбирайте `target`/`contains` по полному имени (`ru.evolenta...#метод(сигнатура)`), а не по фрагменту.
- Ответы инструментов компактны — не пересказывайте их пользователю дословно, давайте вывод (список вызывающих, список эндпоинтов) сжато.
- Если индекс не покрывает вопрос (Groovy-скрипты, ресурсы, XML, динамические вызовы) — не долбить MCP, переходить на grep по исходникам осознанно.
- Перед изменением сигнатуры метода проверять затронутые места сначала через `get_called_by`, потом подтверждать точечным чтением исходника (file:line из индекса).
